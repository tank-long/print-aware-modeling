# 怎样持续更新这个技能

## 用户可以直接这样说

- “把这次经验记到 `$print-aware-modeling`：用了什么方案，打印结果怎样。”
- “更新 `$print-aware-modeling`，这个方法在 PETG 上粘得太牢，记录失败条件。”
- “参考这个 GitHub 链接，先核对实现，再把值得借鉴的部分补进技能。”

图片、切片工程或参数有助于细化记录，但不是接收反馈的前置要求。用户只记得一句总体评价时，先忠实记录这一句；不能因缺参数而抹掉实打事实。

主动发现重复需求、可复用经验与工具化机会。是否持久修改技能库、接入依赖或公开案例，以当前用户或项目的授权为准；已有持续维护授权时直接执行，不重复询问。其他用户的授权不能由本技能继承；不因安装本技能而启动后台学习、定时任务或自动向上游提交内容。

## 由 Agent 消化案例

在用户已授权的技能维护范围内，由 Agent 将原始案例整理成便于检索和迁移的经验，用户无需先填写标准报告。按现有材料完成以下整理，缺失项标“未知”，只追问影响当前判断的信息：

1. 保留原始来源、文件版本和反馈原意；模型项目保留原始事实，技能摘要链接回来源。
2. 提取问题场景、目标、适用条件和保护范围，记录采取的动作、关键参数及结果与代价。
3. 分开写观察事实与机理推断，提炼可迁移思路、需要重新计算的参数及不能推广的范围。一次成功的具体数值不自动成为默认值。
4. 优先补入现有主题参考，合并重复经验并保留失败、矛盾结果及各自条件。在主文件或相关参考补清“遇到什么问题读哪篇”的入口；案例 ID、来源和版本能互相追溯即可，不强制每案一文件或单独建索引库。

## 从经验逐步沉淀可执行能力

三种形式可以叠加，按任务需求、调用者对具体任务的能力及现有软件选择，不按模型名称固定分档：

| 形式 | 沉淀内容 | 何时值得建设 |
|---|---|---|
| 知识与经验 | 结构化案例、设计判断、适用边界和验证方法 | 随真实案例持续补充，帮助选择和评估方案 |
| 通用建模库 | 如 BOSL2 的可运行调用、相关接口示例与结果检查 | 实际任务出现重复几何需求，复用可减少重复实现，且目标环境能执行、导出和回读 |
| 专用生成工具 | 固定脚本或模板、明确参数、输入校验和输出检查 | 某类需求反复出现，输入输出与适用范围足够明确，可将实现封装为少量参数调用 |

先随案例积累知识，在真实需求出现时再接库或封装工具。接入代码后验证实际运行与几何结果；若要证明更易被不同能力的模型使用，用相同代表任务检查实际输出，不能仅凭安装成功推断效果。模型仍需理解需求、选择工具和检查是否满足目标。

维护记录区分“已提炼知识”“已接通库调用”“已有专用工具”。阅读外部源码不代表已具备其运行能力。

## 主动发现重复并落实工具

每次调用本技能都主动检查，无需用户提醒。开工时从当前任务相关的入口比对已有案例、候选和工具，判断能否直接复用；交付前复核本次实现和结果，判断是否新增或推进工具化机会。纯咨询也按其相关场景轻量检查，不全量审计经验库。

检查结论用一句话并入现有交付，说明复用了什么、推进了什么或本次未发现新的工具化需求。无新发现时无需单独写日志、更新STATE或修改技能；有新候选或实现变化时再持久记录。根据检查结果执行以下闭环：

1. **发现重复：** 留意相似结构在不同尺寸/条件下反复生成、同一段几何操作重复编写、同类失误反复修复。回查对应案例、模型版本或实现；同一案例反复被引用不增加使用证据，不设固定出现次数作为门槛。
2. **判断可封装范围：** 明确能减少什么重复工作，哪些输入可以参数化（含单位、范围及相互约束），哪些条件仍需设计判断，以及输出怎样核对。未成熟时把候选、来源和缺失证据简记在现有项目记录或 STATE，后续相关任务再复核。
3. **直接实现最小可用工具：** 条件成立时在已授权范围内完成实现，不停在建议。根据实际环境选择调用现有库或封装专用脚本/模型模板，可直接形成专用工具，无需为了分层先接某个库。优先复用现有工具或项目内依赖，不改无关全局配置。
4. **运行、检查和接回技能：** 用代表参数实际运行，按工具功能检查关键尺寸、几何关系或导出回读；有输入约束时检查不合法参数的处理。保留来源、依赖版本、适用范围和验证结果，在相关场景入口链接到代码，写清调用方式、参数及一个可运行示例，然后校验并同步。工具实现与源记录互相引用，便于后续修正。

汇报识别到了什么重复、为何值得工具化、实际完成到哪一步及验证范围。运行条件受限时保留代码或候选和具体卡点，不把“已写代码”报告为“工具可用”；几何运行成功也不代替切片或实打证据。已有候选在下一次相关使用时继续推进。

## 更新时怎么分配内容

- 稳定的设计判断/工作方式：窄幅修改 `SKILL.md`，说明适用范围。
- 某个模型的一次成功或失败：放在 `references/` 的案例里，补日期、版本、条件和结果，不扩写主文件。
- GitHub/文档中发现的做法：先记来源和实际观察，标为外部候选；未经试打不升级成用户成功经验。
- 与旧结论矛盾的反馈：保留历史经过，修正当前结论和适用范围。原先“尚未实打”在收到实打反馈后必须改正。

## 维护源与个人安装

在 Git 仓库维护技能源文件，安装目录用于日常调用。修改前核对源与安装副本；有分叉时合并本次涉及的内容，不用整目录覆盖较新案例。保留可恢复版本，验证后仅同步 `SKILL.md`、`agents/`、`references/` 及实际新增的技能资源。

原始模型、照片、切片工程与私有协作记录留在各自项目。公开案例使用可访问的来源，或明确标注“维护者项目摘要，原始文件未随仓库分发”；不能留下只在维护者机器上可用的路径。公开材料须在当前授权范围内，保留第三方出处。

公开贡献通过仓库的 [贡献说明](https://github.com/tank-long/print-aware-modeling/blob/main/CONTRIBUTING.md) 提交。只报告实际完成的几何、切片或实打验证；用户的一句总体好评可以记录，但不能扩写为未经确认的细项结果。模型与切片协作共用同一版本的案例事实，具体交接见 [建模与切片交接](slicing-handoff.md)。

完成后说明新增或修正了什么、证据等级和未知条件。已有持续公开同步授权时，按 [持续迭代流程](iteration-workflow.md) 在本次任务内完成 GitHub 同步并核对结果；没有该授权时只完成已获授权的本地维护。安装技能本身不授予发布权限，也不启动后台更新进程。
