# 从实际建模经验到 GitHub 更新

用于任务中的新经验、纠正反馈、重复实现与待同步变更。由当前 Agent 随实际任务执行，不依赖定时任务、后台监听或单独的切片 skill。没有新知识或待处理变更时，不制造提交。

## 1. 确认维护位置与已有约定

从当前任务、项目记录及技能根目录可选的 `LOCAL_MAINTENANCE.md` 确认维护源、安装副本、远程仓库与同步范围。个人配置应留在本地、被 Git 忽略，不能跟随发布包传播。

安装公共 skill 不等于授权向上游提交。当前用户已授权持续同步时，不逐次重复询问常规经验更新；若没有约定，完成已授权的部分，不能由其他人的配置推定授权。仓库不存在、目标不一致或权限变化时，记录具体阻塞，不改投其他仓库。

先检查本地变更和远程最新版本，比较主源与安装副本；保留尚未合并的本地经验。只有当前任务涉及更新时才读取相关状态，不全量扫描用户模型目录或社区反馈。

## 2. 从实际结果提炼经验

建模交付前、收到切片/实打反馈时，检查本次是否产生：新问题与解决方法、原结论的反例、证据等级变化、值得复用的参数关系或重复操作。修正原案例优先于重复建档。

原始事实留在模型项目，至少能追溯：日期与模型版本、问题和保护范围、打印方向、几何动作、关键尺寸及单位、已知工艺、实际观察、未知项与适用边界。用户不必先填模板，由 Agent 消化；没有的信息写未知。

| 获得的证据 | 可以怎样记录 |
|---|---|
| 仅有方案或推导 | 作为候选或假设演练，写清待验证内容 |
| 已回读几何 | 说明测量范围、工具和文件版本，不宣称实打成功 |
| 已检查实际切片 | 记录关键层、路径与配置，不推定强度或易拆 |
| 已收到实打反馈 | 忠实记录样件、条件和反馈原意；缺失工艺仍写未知 |
| 后续失败或矛盾结果 | 保留旧条件，修正当前结论，不删除失败历史 |

候选知识可在明确标注条件下公开，不必等所有项目都实打完成；不能把“证据不足”藏进笼统成功结论。

## 3. 形成最小公开改动

优先补充既有 `references/` 主题或案例。只有影响通用判断和路由时才修改 `SKILL.md`；工具化按 [更新约定](updating.md) 判断并实际运行验证。更新 `CHANGELOG.md` 的 Unreleased，说明用户可见变化，不重复复制私有工作日志。

公开内容以可迁移方法、匿名化案例摘要、已获授权的代码和公开来源为主。发布前逐文件阅读差异：去除个人绝对路径、私有网址、账户信息和不必要的项目标识。需要来源而未公开原件时，标明“维护者项目摘要，原始文件未分发”，在本地保留对应关系。

原始 CAD/STL/3MF、照片、聊天记录、第三方模型和私人协作文件不随经验摘要自动上传。对尚未授权公开的素材，先完成可公开的方法总结；只有确实需要原件才能完成发布时才询问其范围。切片观察可以作为建模证据，不因此把切片 skill 或整套配置一并公开。

## 4. 校验并同步个人安装

- 检查描述与引用是否可达、公开语句是否符合证据、主入口是否还能独立使用。
- 在维护仓库运行 `python3 tools/validate.py` 和 `git diff --check`；有 skill 格式校验器时同时运行。脚本只能覆盖其明示检查项，不能替代逐文件公开审阅。
- 改变设计判断时，用对应的代表场景复核决策与限制；新增工具实际运行并回读结果。文档改进无需伪造打印测试。
- 校验后仅同步本次涉及的运行文件，核对源/安装内容；保护安装侧新增经验及本地配置，不覆盖分叉。新增 `scripts/` 或 `assets/` 时，应同步更新公开文件白名单与校验清单，避免资源未入库。

没有用户可见变化或差异已包含于上游时，结束本次维护，不重复提交。

## 5. 同步 GitHub 并核实结果

在当前公开授权范围内，常规经验补充、文档修正和已验证的小改动可直接提交维护分支。社区贡献或需要评审的结构性变更使用分支与 PR；不得为了提交而放宽证据或校验要求。

发布前再次读取远程分支头，基于最新内容合并本次改动，避免整树覆盖协作者的新文件。只提交已审阅的文件清单，提交说明包含具体问题、变化和验证范围。Git 推送使用普通快进；连接器更新分支应校验预期旧提交。遇到远程前进或拒绝时重新读取并合并，不强制覆盖。

优先使用已连接的 GitHub 工具；连接器可用时无需要求用户重新登录 CLI。API 创建提交后，本地获取远程历史，核对文件差异再对齐，保留本地未发布工作；不能仅因工作树相似就丢弃提交。

远程回读提交及文件树/受影响文件，确认本次内容实际进入目标分支。只有此时才报告“已同步 GitHub”；有本地提交、上传草稿或 PR 待合并时，按其真实状态汇报并附链接。

## 6. 日常提交与正式版本分开

日常改进进入 `main` 和 Unreleased，不为每次反馈创建 Release。README 中安装 `main` 的用户可获取最新内容；已安装副本不会因此自动更新，更新前需保护使用者自己的修改。

一组改进已形成可说明的里程碑、或用户要求发版时，再整理版本：规则修正/案例补充通常增加补丁号，新增独立能力通常增加次版本号；会改变既有使用方式的改动明确写出迁移说明。按实际影响决定，不机械地由文件数量决定版本。

发版时将对应 Unreleased 项移到带版本与日期的条目，先提交，再从该提交制作干净包；标签、Release 与包内容必须对应。下载核对附件摘要，不重写已发布标签或悄悄替换旧包；错误通过新提交或后续修正版纠正。Git 白名单外的本机配置和模型项目记录不得进入包。

## 7. 留下可恢复的状态

在维护源的本地项目记录中，只在有实际变化时记录：案例来源、涉及文件、校验结果、安装同步状态、待同步原因，以及成功后的提交/PR/版本链接。可用“已整理 → 已校验 → 已同步安装 → 已同步远程 → 已发版”区分进度；未要求发版的任务在远程同步后即完成。

网络、权限或冲突阻塞时保留本地成果，记录卡点与下一步；下次相关任务或用户要求继续时重试，先确认远程是否已经成功，避免超时后重复提交。不启动后台重试或承诺离线时也会自动更新。

每次交付用一句话说明：沉淀了什么、证据到哪一步、同步到哪里。无新经验时说明本次复用情况即可。
